## Повторная диагностика локальных тестов

Повторный полный CTest воспроизвёл тот же результат: 17/26 успешны, 8 не
запущены, first_run завершён по тайм-ауту 30 секунд. CodeIntegrity/Operational,
событие 3077, прямо указывает на Enterprise signing level и политику
`{0283ac0f-fff1-49ae-ada1-8a933130cad6}`. Это отказ Windows до выполнения
тестового кода, а не упавшее утверждение теста.

Причину тайм-аута пока установить не удалось: прежний отчёт буферизовался
и оставался пустым при принудительном завершении процесса CTest. В
`src/win32/PreviewTests.inl` добавлены немедленная запись (`std::unitbuf`),
отметки этапов с прошедшим временем и текущие DPI/режим/тема. Срок теста и
его проверки не ослаблены; поведение обычного приложения не менялось.

Сборка диагностического EXE успешна. Его запуск через CTest тоже заблокирован:
событие CodeIntegrity 3077 от 27 октября 2026, 11:11:49 МСК указывает на
`build-release/Release/TriggerLabCapturePreview.exe`. Новую диагностику
поэтому нельзя считать выполненной. Настройки доверия, подписи, политики
безопасности и имена исполняемых файлов не изменялись для обхода блокировки.

Docker CLI установлен, но Linux engine недоступен (`docker info` не соединяется
с dockerDesktopLinuxEngine); дополнительные Linux-тесты не запускались.

Для продолжения нужен разрешённый запуск этих сборок по действующей политике
организации либо отдельная Windows-среда разработки, допускающая локальные
сборки. После этого узкая команда:

```powershell
ctest --test-dir build-release -C Release --output-on-failure -R '^triggerlab_first_run$'
```

Отметки появятся в `build-release/Release/first-run-test-report.txt`; они
позволят отличить медленную матрицу от остановки на конкретном этапе.
